# Codex API 直连与地址探测：现状及边界

这是用户在 .91 发布过程中补充的方案讨论。仅针对 Codex；Claude Code 暂不新增此逻辑。以下内容不是 .91 已实现功能声明。

后续：用户已授权实现，源码及 DeepSeek 官方实测已完成，见[实现与验证记录](codex-api-direct-implementation-2026-10-29.md)。下面保留方案形成时的现状，.91 安装包未包含后续实现。

## 已有实现

- `api-protocol.ts` 为单个模型发微小推理请求，按 Responses / Chat Completions / Anthropic Messages 的响应结构识别协议。快速添加服务对每个模型分别调用，成功后保存 `modelRoutes[真实模型ID]={baseURL,protocol}`；实际转发使用该模型映射。
- 裸域名当前先尝试 `/v1` 再尝试根地址。输入已带 `/v1` 等版本段时只尝试该地址；自定义路径尝试自身及追加 `/v1`。没有自动尝试根地址去掉版本段，也没有自动枚举 `/anthropic`。
- 请求层对 Chat 的 token 限制字段有一次参数兼容重试。成功问答不是 Codex 的完整兼容性验收。
- 当前本地 Agent 产品入口仍写入 TokenFlow provider，尚无通用供应商 API 直连入口。此前只做过隔离可行性研究，见 [研究](codex-direct-api-research-2026-10-28.md)。

## 建议实现

1. 地址候选和协议候选独立生成。优先用户明确输入的地址；同源候选补/去末尾 `/v1`，保留自定义租户路径。`/anthropic` 等额外路径只根据明确协议提示、供应商文档或预设加入，不无限扫描，不改主机或降级 HTTPS。
2. 只在路径/协议不匹配时继续尝试；明确的鉴权、额度、限流、网络故障分开处理，不把这些失败当作模型不存在。所有候选共享取消和总时限，防止每个模型长时间反复试错。
3. 以来源身份＋模型 ID 保存验证成功的 base URL、协议和时间。已有 `modelRoutes` 复用，不另造一套运行路由。更换地址或 Key 时让旧能力结果失效；普通推理不重新探测。
4. Codex 直连要求验证 Responses 的流式终态、工具调用/结果、多轮输入及已知压缩能力。只有 Chat 或 Messages 的模型继续经 TokenFlow 转换；不能因为它们回答过 OK 就开放 Codex 直连。
5. Codex 接入分为官方账号、供应商 API 直连、统一网关。直连写实际供应商 URL 与原始模型 ID，TokenFlow 不转发推理，用量沿用本机日志。直连期间保留官方登录文件，但当前请求使用 API 凭据。
6. 进入统一网关先撤销直连专属 provider、强制 API 登录及模型目录设置，恢复原官方接入配置，再按现有流程启用统一网关。离开直连恢复记录的前像并保留其他设置，不把修改源名称等同于完成路由切换。
7. 旧会话转换仍需满足上下文恢复条件。供应商不能解密 OpenAI 或 TokenFlow 的私有状态；不能仅因 Responses 可用就承诺所有旧会话无缝往返。保留配置/历史备份，先隔离验证再开放迁移。

## DeepSeek 当前文档

2026-10-29 重新核对 [Codex 集成文档](https://api-docs.deepseek.com/quick_start/agent_integrations/codex/)：原生 Responses，provider URL 为 `https://api.deepseek.com/`，模型目录与认证模式均由配置指定。文档还说明官方账号与第三方 API 模式切换可能影响会话可见分组，要求重启客户端；不能只改一个 base URL 就宣称完整接入。没有执行其远程安装脚本。

七牛或其他托管平台的同名模型仍需逐模型验证，不能借用 DeepSeek 官方接口的能力结论。API 直连首次落地的测试应包含配置恢复、官方登录保留、TokenFlow 退出后的请求、取消、流式结束、工具往返、本地摘要与重启续聊。
