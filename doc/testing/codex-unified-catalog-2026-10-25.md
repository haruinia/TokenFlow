# Unified gateway and model picker ordering — .75

The Codex connection UI again exposes `官方账号＋网关模型` as unified gateway mode (`codexCoexist: true`, `codexDirectHybrid: false`). Official direct, gateway-only and the experimental direct/hot-reload mode remain separate, explicitly labelled choices. The confirmation explains that official requests and native compaction go through TokenFlow, third-party compaction uses the summary compatibility layer, and TokenFlow must remain running. The existing production connection/migration/backup path is reused; the normal official app launch is selected for aggregation, not the provider-switch bridge or a replacement engine.

The picker previously interleaved entries because both catalogs started `priority` at zero. `mergeCodexCatalog` now preserves every official entry verbatim and assigns gateway additions priorities above the maximum official priority. Gateway display names have a single `TokenFlow · ` prefix; routing IDs and provider selection remain unchanged. A genuine section-heading field is not available in the inspected native model schema; no fake/selectable heading model is inserted. The final menu therefore retains the official sequence followed by labelled gateway entries, rather than a literal new submenu.

## Deployment boundary

Build/install backs up .74 and records config/auth hashes. The installer does not quit the user's current Codex. The final unified-mode action is exposed in TokenFlow and restarts Codex through the existing migration lifecycle when the user clicks it. Before that action, the currently active connection remains the prior mode. New ordering is applied when the catalog is regenerated by that connection action.
